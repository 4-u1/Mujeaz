## 1. الملخص التنفيذي

مُجاز طبقة ذكاء تشغيلية بين أنظمة المستشفى السريرية (HIS / EMR) والمسار التأميني (NPHIES). يحوّل الطلب السريري إلى طلب **جاهز للقرار** قبل إرساله، ويبحث عن الأدلة الموجودة أصلًا في سجل المريض، ويطابقها مع سياسة الجهة الدافعة. وإذا رُفض الطلب، يبني **حزمة استئناف موثقة بالمصادر** وجاهزة للمراجعة البشرية.

**القيمة المحورية:** مُجاز لا ينتظر الرفض ليبدأ؛ يكتشف أسبابه قبل الإرسال، وإذا وقع يحوّله إلى فرصة استرداد.

```
Clinical Order → Decision-Ready Authorization → Protected Revenue
                                   ↘ (Denied) → Recoverable Revenue
```

## 2. المشكلة

ثلاث عمليات تعمل منفصلة: **القرار السريري**، و**الموافقة التأمينية**، و**دورة الإيرادات**. فيُرفض أو يتأخر طلب صحيح طبيًا بسبب:

- دليل سريري غير مذكور صراحة في الطلب، رغم وجوده في السجل.
- شرط في وثيقة التأمين لم يُستوفَ أو لم يُوثَّق.
- خطأ أو نقص في الترميز، أو عدم تطابق التشخيص مع الإجراء.
- مرفق مطلوب لم يُرفق.
- عدم تطابق البيانات بين السجل والطلب، أو أخطاء إدارية.

**النتيجة:** تأخير الرعاية، وعبء إداري، وتأخر التحصيل، وتسرب الإيرادات.

**الفجوة:** أنظمة الموافقات الحالية ترسل الطلب دون فهم السياق السريري، وأنظمة الاستئناف تبدأ بعد وقوع الخسارة. لا يوجد ما يربط المرحلتين.

## 3. الأهداف وما هو خارج النطاق

### 3.1 أهداف المنتج

| # | الهدف | المؤشر |
|---|---|---|
| G1 | رفع نسبة الطلبات النظيفة من المحاولة الأولى | First-Pass Clean Rate |
| G2 | اكتشاف أسباب الرفض قبل الإرسال | Denial Prevention Rate |
| G3 | تقليل وقت تجهيز الطلب | Time to Decision-Ready |
| G4 | استرداد الإيراد المرفوض | Revenue Recovered, Overturn Rate |
| G5 | قابلية التتبع الكاملة لكل توصية | % من الحقائق المرتبطة بمصدر = 100% |

### 3.2 خارج النطاق (Non-Goals)

- مُجاز **ليس** جهة تأمين ولا جهة تحكيم مطالبات ولا جهة اعتماد NPHIES.
- **لا** يتخذ قرارًا سريريًا ولا يعدّل خطة العلاج.
- **لا** يرسل أي طلب أو استئناف دون مراجعة بشرية في الـMVP.
- **لا** يقترح ترميزًا بهدف رفع قيمة المطالبة (Upcoding)؛ هدفه **سلامة الترميز** لا تعظيمه.
- **لا** يضمن موافقة الجهة الدافعة؛ مؤشر الجاهزية يقيس اكتمال الطلب، لا احتمال القبول.

## 4. المستخدمون (Personas)

| الشخصية | الدور | ما يحتاجه من مُجاز |
|---|---|---|
| **موظف الموافقات المسبقة** | يجهّز الطلبات ويرسلها | قائمة نواقص واضحة، أدلة جاهزة بمصادرها، طلب نظيف من أول مرة |
| **الطبيب المعالج** | يكتب الطلب السريري | أقل قدر من الإزعاج؛ سؤال توثيق واحد محدد عند الحاجة فقط |
| **أخصائي الترميز** | يراجع الأكواد | تنبيهات عدم التوافق بين التشخيص والإجراء |
| **مسؤول الاستئنافات** | يتابع المرفوض | سبب الرفض الجذري، خريطة أدلة، مسودة خطاب، مواعيد نهائية |
| **مدير دورة الإيرادات / المدير المالي** | يتابع الأداء | الإيراد المعرض للخطر، المحمي، المسترد، وأنماط الرفض |
| **مسؤول الامتثال** | يدقق | سجل تدقيق كامل لكل قرار وكيل ومدخلاته ومخرجاته |

## 5. نطاق الـMVP

**سيناريو واحد كامل من البداية إلى النهاية:** طلب **MRI للفقرات القطنية** لمريض ألم أسفل الظهر.

| داخل الـMVP | خارج الـMVP |
|---|---|
| استيراد طلب سريري + سجل مريض تجريبي (FHIR Bundle) | تكامل مباشر مع HIS حقيقي |
| A1 → A6 كاملة لهذا السيناريو | إجراءات أخرى (CT، مناظير، أدوية تخصصية) |
| سياسة تأمين تجريبية واحدة مصاغة كقواعد + نص | قاعدة سياسات متعددة الجهات |
| مؤشر جاهزية حتمي قابل للشرح | نموذج تنبؤ مدرّب على بيانات حقيقية |
| بناء FHIR Bundle والتحقق منه محليًا | إرسال حقيقي إلى NPHIES |
| استجابة جهة دافعة **محاكاة وموسومة بوضوح** | — |
| حزمة استئناف + مراجعة بشرية | إرسال آلي للاستئناف |
| قاعدة بيانات، مصادقة، أدوار، سجل تدقيق | تعدد المنشآت (Multi-tenant) الكامل |

## 8. المعادلات والتعريفات

### 8.1 مؤشر جاهزية مُجاز (Mujeaz Readiness Score)

يقيس **اكتمال الطلب**، لا احتمال قبوله.

| المكوّن | الوزن المقترح | طريقة الحساب |
|---|---|---|
| Clinical Evidence | 30% | نسبة متطلبات الأدلة بحالة `FOUND` (PARTIAL = نصف) |
| Policy Match | 25% | نسبة القواعد `PASSED` (WARNING = نصف) |
| Documentation | 15% | اكتمال الحقول السريرية الإلزامية |
| Coding Integrity | 15% | صحة الأكواد وتوافق التشخيص مع الإجراء |
| Required Attachments | 10% | المرفقات المطلوبة الموجودة ÷ المطلوبة |
| Administrative Completeness | 5% | بيانات المريض والتغطية والمنشأة |

**بوابات صارمة (Hard Gates):**
- أي قاعدة إلزامية بحالة `FAILED` ← سقف المؤشر 60.
- كود غير صالح أو غير متوافق ← سقف المؤشر 50.

**التصنيف:** ≥ 90 جاهز للقرار · 70–89 يُنصح بإجراء · < 70 يتطلب إجراء.

**قاعدة الشرح:** أي مؤشر أقل من 100 يُعرض معه **سبب كل نقطة مفقودة** والإجراء الذي يرفعها.

### 8.2 مؤشرات الإيراد

| المؤشر | التعريف |
|---|---|
| Financial Value | سعر الخدمة المتعاقد عليه مع الجهة الدافعة |
| Denial Risk (p) | احتمال الرفض؛ في الـMVP تقدير قائم على القواعد (نواقص وبوابات)، لاحقًا نموذج مدرّب |
| Revenue at Risk | Financial Value × p |
| Recoverable Value | للحالات المرفوضة: Financial Value × احتمال قلب القرار المقدّر |
| Revenue Protected | مجموع قيم الطلبات التي اكتُشفت مخاطرها وصُحّحت ثم قُبلت |

> **ملاحظة للعرض:** الأرقام يجب أن تكون واقعية للخدمة. مثلًا قيمة MRI قطني منفرد بضعة آلاف ريال، لا مئات الآلاف. الأرقام الكبيرة تُعرض على مستوى **المحفظة** (مجموع طلبات القسم أو الشهر)، لا على مستوى طلب واحد.

## 9. المعمارية المستهدفة

```
┌─────────────── Frontend (React/Next.js · TS · Tailwind · RTL-first) ───────────────┐
│ Command Center · Work Queue · Case/Digital Twin · Evidence Viewer · Recovery       │
└──────────────────────────────────────┬─────────────────────────────────────────────┘
                                       │ REST / WebSocket (auth: OIDC + RBAC)
┌──────────────────────────────────────▼─────────────────────────────────────────────┐
│ API Gateway (FastAPI)                                                              │
│  ├── Orchestrator (state machine لكل حالة؛ بديل n8n للمنطق الحساس)                  │
│  ├── Agents A1–A6 (LLM + Structured Outputs)                                        │
│  ├── Rules Engine (قواعد حتمية مُصدَّرة ومختبرة)                                    │
│  ├── Scoring Service (المعادلات في القسم 8)                                          │
│  ├── FHIR Service (بناء + تحقق NPHIES profiles)                                     │
│  └── Audit Service (hash-chained log)                                               │
└───────┬──────────────────────┬──────────────────────┬──────────────────────────────┘
        │                      │                      │
┌───────▼───────┐   ┌──────────▼──────────┐   ┌──────▼──────────────────┐
│ PostgreSQL    │   │ pgvector            │   │ Integration Layer       │
│ + RLS لكل منشأة│   │ (سياسات + سجل طبي)  │   │ HIS/EMR (FHIR/HL7v2)    │
│               │   │                     │   │ NPHIES Gateway          │
└───────────────┘   └─────────────────────┘   └─────────────────────────┘
```

**قرار معماري:** n8n مقبول للنموذج الأولي فقط في التكاملات غير الحساسة (إشعارات، جدولة). **منطق الوكلاء والقواعد والتقييم يعيش في خدمات Python** مختبرة ومُصدَّرة؛ لأن سير العمل البصري يصعب اختباره وتدقيقه.

## 10. نموذج البيانات

| المجال | الجداول |
|---|---|
| السريري | `patients`, `encounters`, `clinical_documents`, `clinical_notes`, `diagnoses`, `procedures`, `medications`, `clinical_facts` |
| الأدلة | `clinical_evidence`, `evidence_spans` (مستند + بداية + نهاية) |
| السياسات | `payers`, `payer_policies`, `policy_versions`, `policy_rules`, `policy_chunks` (embeddings) |
| الموافقات | `authorization_requests`, `authorization_requirements`, `authorization_evidence`, `authorization_events` |
| الجاهزية والمخاطر | **`readiness_scores`** (بدل `q_scores` غير المعرّف)، `revenue_risk`, `price_lists` |
| المطالبات والرفض | `claims`, `denials`, `denial_reasons` (مربوطة بأكواد NPHIES)، `appeals`, `appeal_evidence`, `recovery_cases`, `deadlines` |
| التشغيل | `agent_runs`, `prompts` (مُصدَّرة)، `human_reviews`, `audit_logs`, `nphies_transactions` |
| الهوية | `organizations`, `facilities`, `users`, `roles`, `permissions` |

كل جدول يحمل `organization_id` مع **Row-Level Security** لفصل بيانات المنشآت.

## 11. المتطلبات غير الوظيفية

| الفئة | المتطلب |
|---|---|
| الأداء | تحليل طلب كامل (A1→A5) < 30 ثانية (p95)؛ فتح الحالة < 1 ثانية |
| التوفر | 99.5% للـMVP |
| الإقامة | استضافة البيانات داخل المملكة |
| اللغة | واجهة عربية RTL أولًا مع الإنجليزية؛ أرقام وتواريخ وعملة بتنسيق محلي |
| الوصولية | WCAG 2.1 AA |
| المراقبة | تتبّع لكل تشغيل وكيل: الزمن، التكلفة، الأخطاء، معدل الرجوع للبديل |
| قابلية التكرار | تشغيل نفس الحالة بنفس الإصدارات يعطي نفس المؤشر |

## 12. الأمان والخصوصية والامتثال

- **التنظيم:** نظام حماية البيانات الشخصية (PDPL) ولائحته، متطلبات مجلس الضمان الصحي (CHI) للتكامل مع NPHIES، ضوابط الهيئة الوطنية للأمن السيبراني (NCA)، ومبادئ أخلاقيات الذكاء الاصطناعي الصادرة عن سدايا.
- **تقليل البيانات:** إرسال أقل قدر ممكن من بيانات المريض للنموذج؛ إخفاء المعرّفات (de-identification) قبل الاستدعاء حيث أمكن.
- **مزوّد النموذج:** اتفاقية معالجة بيانات، عدم استخدام البيانات للتدريب، ويفضّل نموذج مستضاف محليًا أو إقليميًا للإنتاج.
- **التحكم بالوصول:** RBAC بأدوار: طبيب، موظف موافقات، مرمّز، مسؤول استئنافات، مدير، مدقق.
- **التشفير:** TLS 1.2+ أثناء النقل، AES-256 أثناء التخزين، والمفاتيح في خادم إدارة أسرار.
- **أمن النماذج:** حماية من حقن الموجّهات (Prompt Injection)؛ نص الملاحظة السريرية يُعامل كبيانات داخل حدود واضحة، والمخرجات تُتحقق بمخطط صارم.
- **المدخلات:** تحقق بمخطط (zod/pydantic) لكل نقطة API، حدود حجم، تحديد معدل الطلبات، وعدم كشف تفاصيل الأخطاء الداخلية.

### مبدأ "No Evidence, No Claim"

كل حقيقة = **Fact + Source + Span + Date + Confidence**. إن لم يوجد دليل يُعرض `MISSING` ولا يُولَّد بديل. **وضع البديل (Fallback) يجب أن يُعلن نفسه** في الواجهة ولا يُعرض كتحليل حقيقي.

## 19. أسئلة مفتوحة

1. ما المنشأة التجريبية الأولى، وما نظام HIS المستخدم فيها؟
2. هل يكون التكامل مع NPHIES مباشرًا أم عبر مزوّد HIS معتمد؟
3. أي نموذج لغوي يُعتمد للإنتاج مع متطلبات إقامة البيانات؟
4. نموذج التسعير: اشتراك فقط، أم مكوّن مرتبط بالاسترداد (يحتاج مراجعة تنظيمية وتعاقدية)؟
5. من يملك صياغة وتحديث قواعد السياسات داخل المنشأة؟
